# Excel マクロ（VBA）の xljs への移植

VBA を **1 行ずつ訳さない**。マクロが「何を読んで、何を作るか」をつかみ、xljs で素直に書き直す。
xljs の API・回答の決まり（フォーム、入力チェック、新しいファイルに保存など）は `prompt.md` と `reference.md` に従う。ここに書くのは移植に特有の決まりだけ。

## 進め方

1. **読む**: モジュール全体を読み、エントリポイント（ボタンに割り当てられた Sub、`Workbook_Open` など）から実際に呼ばれる処理だけをたどる。
2. **説明する**: 次を箇条書きで先に書く。
   - 入力（どのブック・シート・列、利用者が入力・選択するもの）
   - 出力（どのファイル・シート・列、上書きか新規か）
   - 処理の中身（業務の言葉で。「売上シートを担当者ごとに集計して…」）
   - 移植しないもの（後述の「捨てるもの」）と、xljs では再現できないもの
3. **設計を見直す**（後述）。改善できる点があれば、コードの前に「提案」として書く。
4. **コードを書く**: 提案が利用者の判断を要するもの（手順や出力が変わるもの）なら、元の動作どおりのコードを出し、提案は「こうもできます」と添える。明らかに無駄な処理（出力に影響しない）は黙って省いてよいが、「省いたもの」に一言書く。
5. 最後に、元のマクロとの違い（省いたもの・変えたもの・できないもの）を短くまとめる。

## 素直に書く（VBA の高速化の工夫は持ち込まない）

xljs は Excel を COM で操作しているのではなく、ファイルをメモリに読み込んで直接扱う。**セル 1 つの読み書きは速い**。
VBA で遅さを避けるために書かれた工夫は、目的ごと捨てて、いちばん読みやすい形で書く。

| VBA でよく見る書き方 | xljs での書き方 |
|---|---|
| `arr = Range("A1:F1000").Value` で配列にコピー → 配列を編集 → `Range(...).Value = arr` で書き戻す | 表なら `sheet.toObjects()` で列名で読み、結果は `sheet.write(rows)`。1 セルずつなら `sheet.cell(r, c).value` をそのまま読み書きしてよい |
| `Application.ScreenUpdating = False`、`Calculation = xlCalculationManual`、`EnableEvents = False`、`DoEvents` | 消す（画面も再計算もない） |
| `Cells(Rows.Count, 1).End(xlUp).Row` で最終行を求めてループ | `for (const r of sheet.toObjects())`。番地が必要なら `sheet.rowCount` |
| 列番号を定数や `Match` で求める（`colKingaku = 5`） | 見出しの名前で読む（`r.金額`） |
| `Dictionary` / `Collection` / `VLookup` / `Match` | `Map`、配列、`Object.groupBy` |
| 作業用シートに一時的に貼り付けて並べ替え・フィルター・重複削除 | 配列の `sort` / `filter` / `Set` |
| `ReDim Preserve` で配列を伸ばす | `push` |
| `Union` でまとめて削除、行を下から消すループ | 残す行を `filter` して新しいシートに書く |
| `Format`・`CDate`・`DateSerial` での日付計算 | `dayjs` |
| `On Error Resume Next` で握りつぶす | 必要な所だけ `try` / `catch`。失敗はログに出す |

```js
// VBA: 配列にコピーして単価×数量を計算し、書き戻す
// → 表として読み、列を足して新しいシートに書く
const rows = sheet.toObjects().map((r) => ({ ...r, 金額: (Number(r.単価) || 0) * (Number(r.数量) || 0) }));
out.addSheet("明細").write(rows, { table: true, columnStyles: { 金額: { format: "#,##0" } } });

// 決まった書式の帳票に値を入れるなら、セルを直接書いてよい（配列にまとめなくてよい）
tpl.cell("B3").value = customer;
tpl.cell("F3").value = dayjs().toDate();
```

## 捨てるもの

VBA のマクロには、使われていないものや意味のない処理が多い。**移植しない**。

- どこからも呼ばれていない `Sub` / `Function`、ボタンに割り当てられていない試作・旧版（`Sub 集計_old()`、`Test1`）
- 宣言だけで使われていない変数・定数、値を入れても後で読まれない変数
- 出力に影響しない処理: 選択（`Select` / `Activate`）、スクロール、ステータスバー表示、作業用シートの作成と後始末、最後にまた消す書式
- 同じ処理のコピー＆ペースト（引数違いの Sub が 12 か月分ある、など）→ 1 つの関数とループにまとめる
- コメントアウトされたコード

省いたものは「省いたもの」として名前を挙げる（利用者が「あの処理はどこへ？」と迷わないように）。判断がつかないもの（シートのボタンから呼ばれているかもしれない、など）は残すか、利用者に確かめる。

## 設計を見直す（申し出てから提案する）

マクロは「手作業の一部だけを自動化した」ものが多い。全体の流れを見て、次のような点があれば **コードの前に「提案」として**書く。勝手に手順を変えず、元の動作と提案の違い（利用者の操作がどう変わるか）を示して選んでもらう。

- **人の操作が何度も挟まる**: 「マクロ 1 を実行 → 手でファイルを開いてコピー → マクロ 2 を実行 → 手で並べ替え → マクロ 3」のような流れは、入力をフォーム 1 画面で受け取り、1 回の実行にまとめられないか。人の判断が本当に必要な所（対象の選択、確認）だけを `ui.table` の選択や `confirm` で残す。
- **途中の手順が無駄**: 入力と最終的な出力を比べて、途中の中間ファイル・作業シート・転記が要らないなら、入力から出力を直接作る。例: CSV を一度シートに貼り付けて整形し、別シートに転記してから集計 → `csv.read` から直接集計。
- **毎回手で書き換える値**: コード中の年月・パス・シート名を毎回直している形跡があれば、フォームの入力項目にする。
- **元のファイルを上書きしている**: 新しいファイルに保存する形を提案する（Excel で開いていると保存できず、失敗時に元に戻せないため）。

提案の書き方の例:

> **提案**: 元のマクロは「取込」「整形」「集計」の 3 つを順に実行し、間で手作業のコピーが必要でした。最終的な集計表は元の CSV だけから作れるので、CSV と保存先を選ぶフォーム 1 つにまとめました。途中の「整形」シートが別の用途で必要なら、出力に残す形にもできます。

## xljs で再現できないもの

はっきり「できません」と書き、代わりを示す。

- 開いている Excel の操作（`ActiveSheet`・`Selection`・選択範囲を対象にする処理）→ 対象のブック・シートをフォームで選ばせる
- シートのイベント（`Worksheet_Change` など）、シート上のボタン → スクリプトを実行するたびに処理する
- 印刷・PDF 出力、グラフ・ピボットテーブルの作成、図形
- Outlook・Word など他のアプリの操作、Web へのアクセス
- 保存すると VBA は失われることがある（.xlsm に書き戻さず、別の .xlsx に出す）
